### 1.3 Architecture pattern

Classic **Clean/Onion Architecture** (Jason-Taylor-template shaped):

- `Domain` — entities, value objects, in-memory domain events (`IHasDomainEvents`), no persistence concerns.
- `Application` — CQRS via [`Mediator`](https://github.com/martinothamar/Mediator) (source-generated, not MediatR), one command/query per file, `AbstractResult` + `Message` list for structured success/warning/error feedback, a single `MetricsBehaviour` pipeline behavior.
- `Infrastructure` — EF Core with **two DbContexts** (`IReadDatabaseContext` / `IReadWriteDatabaseContext`, both currently backed by the same Postgres instance — a read/write split, not yet a read replica), OpenTelemetry wiring (traces → OTLP/Jaeger, metrics → Prometheus exporter, a custom `Meter`/`ActivitySource` named `"ELifeRPG"`).
- `Api` — ASP.NET Core Minimal APIs, one static `*Endpoints` class per feature, AutoMapper `Profile` per feature for entity↔DTO mapping, responses wrapped in `ResultDto<T> { Data, Messages[] }`.
- `WebUI` — separate Blazor Server project, own auth, own DB access (same `AddInfrastructure`).
- `Migrator` — separate console entrypoint for `dotnet ef` + seeding, since `Api`/`WebUI` don't own migrations directly.

**Notably already present:** OpenTelemetry (traces to Jaeger via OTLP, metrics via Prometheus exporter), a custom `Meter`/`ActivitySource`, Scalar for OpenAPI docs. This directly validates the OTel decision in [ARCHITECTURE.md §9d](./ARCHITECTURE.md#9d-observability) — it's a continuation of an existing pattern, not a new one.

**Critical finding — no identity/authorization boundary on the game-facing API:** `Api/Program.cs` never calls `UseAuthentication()`/`UseAuthorization()`. `POST /v1/sessions` accepts a raw `Guid BohemiaId` in the request body from whatever calls it, with no client authentication, and creates an `Account` if none exists. Likewise `characterId` is taken as a plain query parameter on the banking endpoints with no proof it belongs to the caller. This is precisely the gap [ARCHITECTURE.md §2](./ARCHITECTURE.md#2-core-problem-identity) and [§4.3](./ARCHITECTURE.md#43-player-identity-token-exchange) exist to close — a raw Bohemia ID is currently accepted as a bearer credential in itself.

**Operational quirk worth preserving:** `Api/Program.cs` has a middleware "quick fix" — the Reforger engine cannot set arbitrary request headers, so it always sends `Content-Type: application/x-www-form-urlencoded` even when the body is actually JSON; the old API rewrites the header before routing. This is hard-won knowledge, not incidental code. In the new architecture this concern belongs in the **Bridge Service**, not the Central API — the mod only ever talks to the Bridge over localhost, so the Bridge can simply always parse the mod's body as JSON on its local listener rather than patching headers on a public-facing API.

## 2. Architecture Comparison

| Concern | Legacy (ELifeRPG/Core) | New (eliferpg-core / ARCHITECTURE.md) | Verdict |
|---|---|---|---|
| Game↔backend trust | Mod calls `Api` directly; raw `BohemiaId` accepted as-is | Mod → Bridge (local, credentialed) → Central API; Bridge asserts identity, Token Exchange (RFC 8693) mints scoped player tokens | **New wins outright** — this is the exact vulnerability class the rewrite exists to fix |
| AuthN/AuthZ | None on `Api`; Discord-only cookie auth on `WebUI` | Keycloak OIDC for everyone; Client Credentials (Bridge, NPC module), Auth Code+PKCE (Admin UI) | **New wins** — old app has no machine-to-machine auth story at all |
| Persistence model | EF Core CRUD entities; domain events collected on entities but **no dispatcher found** — likely dead code | Marten event streams on Postgres; events are the source of truth, projections are derived | **New wins** — but the old app's domain events (`AccountCreatedEvent`, `AccountLockedEvent`, ...) map almost 1:1 onto Marten stream events, so this is a low-friction port, not a redesign |
| CQRS | `Mediator` (source-gen), one handler per request | Not yet specified — Central API is a resource server per ARCHITECTURE.md §3.3 | Keep the *shape* (one handler/use-case per file) even without importing the `Mediator` package verbatim; it's a good pattern independent of the event-sourcing switch |
| API contract | Hand-maintained DTOs + AutoMapper profiles per consumer; `ResultDto<T>` envelope | OpenAPI-first, Kiota-generated clients per consumer (§9c) | **New wins** — codegen removes an entire class of hand-sync bugs; envelope pattern replaced by idiomatic REST + problem+json (per your decision below) |
| Real-time delivery | None — polling only | Marten subscription → SignalR, with `GET /events?since=` catch-up | **New wins** — old app has no push mechanism for NPC module or Admin UI to build on |
| Observability | Already has OTel traces (Jaeger/OTLP) + Prometheus metrics + custom `Meter` | OTel → Grafana/Loki/Tempo/Prometheus (§9d) | **Direct continuation**, not a change — old app's `Activities`/`Metrics` static classes are a fine starting point to port forward |
| Admin surface | Blazor Server + MudBlazor, Discord-only login | Vue SPA, Keycloak Auth Code+PKCE | **New wins on auth model**; UI framework change is a rewrite either way since Blazor Server ≠ Vue |
| Deployment | Single `compose.yml` (Postgres, pgAdmin, Jaeger) | Compose now, Kubernetes-ready later (§9a) | New is a superset — old app's compose can mostly be absorbed as-is (swap Jaeger for the Tempo/Loki/Grafana/Prometheus stack) |

**Net assessment:** the new architecture should be preferred wholesale, as planned. The one place the legacy app already got something *right* worth explicitly carrying forward is **OpenTelemetry instrumentation being present from the very first commit**, not bolted on later — ARCHITECTURE.md §9d already commits to the same discipline.

## 3. Second Rewrite Attempt: `rewrite-in-rust-kekw` Branch

**Source analyzed:** [ELifeRPG/Core](https://github.com/ELifeRPG/Core) @ `rewrite-in-rust-kekw` (commit `a35da9c`, one commit ahead of `main`, titled "kekw as code" — despite the branch name, it's still C#/.NET, not Rust).

### 3.1 What's there

The branch stops well before reaching an HTTP surface — there's no `Api`, `WebUI`, or `Migrator` project at all, only `Domain`, `Application`, `Infrastructure`, plus a standalone `tools/CodeGenerator` Roslyn source-generator project. It's an early, abandoned prototype of one thing: **how to do event sourcing without EF Core**.

| Piece | What it does |
|---|---|
| `Domain/Accounts/Account.cs` | `Account.Create(GameId)` factory raises `AccountCreatedEvent`; `Account.Create(IEnumerable<DomainEvent>)` replays events via `Apply(...)` to rebuild state — a hand-rolled event-sourced aggregate |
| `Domain/Accounts/AccountId.cs`, `GameId.cs` | `[StronglyTypedId] partial struct` — strongly-typed IDs instead of raw `Guid` |
| `Application/Common/EventStore/IEventStore` | `AddToStreamAsync` / `ReadStreamAsync` abstraction over an event store |
| `Infrastructure/.../KurrentDbEventStore.cs` | Implements `IEventStore` against **KurrentDB** (formerly EventStoreDB) via `KurrentDB.Client`, a dedicated event-store product — `compose.yml` runs it as its own container alongside Postgres |
| `tools/CodeGenerator/*` | Three custom Roslyn incremental source generators: `DomainEventRegistryGenerator` (scans the `Domain` assembly for all concrete `DomainEvent` subclasses → `DomainEventRegistry.EventTypes`), `DomainEventResolverGenerator` (generates a type-name→deserializer dictionary, `DomainEventResolver.Resolve(typeName, data)`), `EventDispatcherGenerator` (for any `partial class : AggregateBase` with `Apply(FooEvent)` overloads, generates the `override void Apply(DomainEvent)` switch-dispatch boilerplate) |
| `Application/Accounts/AccountQuery.cs` | Still uses `OneOf`/`OneOfBase<Account>` for the query response shape |
| `Application`/`Domain` | Still use `Mediator` (source-generated) — same choice as `main` |

Test coverage is a single source-generator smoke test with no assertions (`tests/CodeGenerator.UnitTests/UnitTest1.cs` runs the generator and drops the result on the floor).

### 3.2 Assessment against the Marten-based direction

This branch chose a **dedicated event-store product (KurrentDB)** plus **three hand-written Roslyn source generators** to compensate for not having a library that already understands event sourcing:

- The registry/resolver generators exist to hand-roll a type-name↔deserializer mapping — this is exactly what Marten's own event-type registration (`options.Events.AddEventType<T>()` / assembly scanning) already provides.
- The dispatcher generator exists to hand-roll `Apply(DomainEvent)` double-dispatch from a set of `Apply(FooEvent)` overloads — this is exactly the convention Marten's own single-stream aggregation already understands natively (an aggregate with `Apply`/`Create`/`Should Delete` methods, projected via `SingleStreamProjection<T>` or Marten's "self-aggregate" support), no custom generator required.
- Running KurrentDB is a second specialized database product to operate (its own container, client library, backup/ops story) for what was, at the time, a single-node early-stage project — precisely the operational cost [ARCHITECTURE.md §5.2](./ARCHITECTURE.md#52-storage-marten-on-postgresql) chose to avoid by picking Marten-on-Postgres over a dedicated event-store product. Your direction this round (Marten, not KurrentDB) formally settles that question in favor of the lighter-weight option.

**Verdict: discard the event-store plumbing, keep the domain-modeling shape.**

- **Discard:** `IEventStore`/`KurrentDbEventStore`, `DomainEventConverter`, `DomainEventResolver`, and all three `tools/CodeGenerator` generators. Marten replaces every one of these responsibilities out of the box; reimplementing them by hand against Marten would be solving an already-solved problem.
- **Keep:** `StronglyTypedId` for aggregate IDs (orthogonal to the event-store choice, cheap, prevents ID-mixup bugs, works fine as a Marten identifier) — carried into [ARCHITECTURE.md §7](./ARCHITECTURE.md#7-technology-stack-summary) and [§9e](./ARCHITECTURE.md#9e-modulith-structure--module-boundaries). Keep the `Account.Create(...)` factory + `Apply(FooEvent)`-per-event shape — it maps directly onto how a Marten-projected aggregate is written, so this part of the branch was pointed the right direction even though the plumbing around it wasn't.
- **Superseded by your directives this round:** `OneOf` → .NET union types; `Mediator` choice is already correct and unchanged.

## 4. Updated Architecture Decisions (This Round)

Folded into [ARCHITECTURE.md](./ARCHITECTURE.md) as a result of this analysis:

| Decision | Where | Rationale |
|---|---|---|
| Central API restructured as a **modulith**: one module per bounded context (`Account`, `Banking`, …), each with its own `Domain`/`Application`/`Infrastructure`/**`Api`** project, composed by a thin `src/Api` host that references only each module's `Api` project | [§9e](./ARCHITECTURE.md#9e-modulith-structure--module-boundaries) | Keeps Clean/Onion layering (kept per your instruction) but applies it per bounded context all the way to the HTTP surface, so a module boundary is enforced by the project-reference graph and is extractable into a real service later without a rewrite |
| **AutoMapper removed entirely** — DTOs live in each module's `Api` project and carry their own static `Create(source)` / `ToCommand()` mapping methods | §9e | Both legacy branches used AutoMapper `Profile` classes for this; colocating the mapping with the DTO removes an indirection layer and a runtime-reflection dependency for something that's just a handful of property assignments |
| **`Mediator`** (martinothamar, source-generated) confirmed, **not MediatR** | §7, §9e | Already the choice in both prior branches — no change, just made explicit for the new project too |
| **.NET 11 preview native `union` types**, `OneOf` dropped entirely (no fallback) | §7, §9e | Both prior branches used `OneOf`; verified the real `union Name(CaseType1, CaseType2, ...)` grammar (found by grepping the Roslyn compiler binary after two wrong guesses — `union Result { ... }` isn't valid, and `closed record` hierarchies are a real but different, narrower feature) — construction, implicit conversion, `switch` pattern matching, and genuine exhaustiveness checking (`CS8509` names the specific missing case) all confirmed working. Used for every Mediator result with more than one meaningful outcome, not just this one endpoint. Pin the exact preview version in `global.json` since preview language features can shift between releases |
| **Marten (not KurrentDB)** confirmed as the event store, one store/schema per module | §5.2 (unchanged from the original spec), §9e | `rewrite-in-rust-kekw` tried KurrentDB + hand-rolled generators instead; this round formally settles that in favor of Marten, per §3.2 above |

## 5. Migration Plan: Feature 1 — Accounts / Sessions

**Why this one first:** it's the smallest closed slice (one aggregate, one use-case) and it *is* the identity problem the new architecture exists to solve — migrating it forces the Bridge + Keycloak + Token Exchange path to actually get built, and every other feature (Characters, Banking, Companies) depends on Account identity, so this unblocks them rather than being throwaway scaffolding. It also happens to be the one slice both prior attempts left the most groundwork for (legacy `main` has the full CRUD version; `rewrite-in-rust-kekw` has an event-sourced `Account` aggregate skeleton).

**Scope of this slice:** replace `POST /v1/sessions` (raw BohemiaId, no auth) with a Bridge-mediated, token-exchange-based session bootstrap, implemented as the `Account` module of the new modulith. Discord-linked accounts (`DiscordId` path) are explicitly **out of scope** — matches ARCHITECTURE.md §1.2's non-goal on player-facing account linking.

### 5.1 Steps

1. **Keycloak realm setup — done and verified** (§4.3)
   - `eliferpg` realm (this dev instance's one tenant realm, per §4.1's tenancy model — a second tenant would be an entirely separate deployment, not a second realm here), `token-exchange` + `admin-fine-grained-authz` features enabled on the Keycloak container.
   - `gameserver-dev` Client Credentials client (standing in for one gameserver instance's own client id, per §3.2/§4.2), `gameserver:session:create` default client scope, `impersonation` client role (from `realm-management`) granted to its service account — this combination is what actually makes `requested_subject` token exchange work, per the verified finding in §4.3. Granting the same tenant's Bridge instances impersonation over the same tenant's players (and, structurally, its staff) is accepted as safe per §4.3 — no further scoping needed.
   - `players` group created; not currently load-bearing for authorization (kept for future use, e.g. Admin UI listings), since the tenancy model is what bounds impersonation, not group membership.
   - Realm exported to `infra/keycloak/eliferpg-realm.json` (dev client secret patched back in post-export, since Keycloak redacts secrets on export) and confirmed to fully reproduce the working setup via `--import-realm` against an empty database.
   - **Consequence for Phase 3–5 below:** the Account module must create a real Keycloak user (not just an internal Marten-projected record) for every new Bohemia ID, since impersonation-based exchange requires an actual Keycloak user to impersonate.

2. **Modulith skeleton — done and runtime-verified** (in this repo, per ARCHITECTURE.md §9b/§9e)
   - `src/Accounts/{Accounts.Domain, Accounts.Application, Accounts.Infrastructure, Accounts.Api}` plus the thin `src/Api` host, all under one `.slnx` (the preview SDK's `dotnet new sln` now defaults to the new XML solution format), targeting **.NET 11 preview** (pinned exactly, not `latestMinor`, in `global.json`). `src/Bridge` is still pending (§5.1 step 6).
   - `src/Api` references only `Accounts.Api` (no direct reference to `Accounts.Domain`/`Application`/`Infrastructure`), wires `Microsoft.AspNetCore.Authentication.JwtBearer` against the Keycloak realm's OIDC discovery document, and calls `services.AddAccountModule(...)` / `app.MapAccountModule()` from `Accounts.Api`. Verified running for real (not just compiled): OpenAPI doc + Scalar docs UI both serve correctly, an unauthenticated request to the session-bootstrap endpoint is `401`, and OpenTelemetry actually reaches the collector — traces for the full Bridge-token → endpoint → `CreateSessionCommand` handler → outbound Keycloak HTTP calls round-trip appear correctly nested in Tempo, and the custom `account_request_counter` metric from `MetricsBehaviour` shows up in Prometheus. One real bug caught and fixed along the way: `JwtBearer` refuses to even initialize against a plain-HTTP Keycloak authority unless `RequireHttpsMetadata` is explicitly disabled for `Development` — omitting it doesn't just fail auth, it 500s *every* request (including unrelated ones like the OpenAPI doc), since `AuthenticationMiddleware` resolves the handler options on every request regardless of whether that endpoint requires authorization.
   - Port `Activities`/`Metrics` static helpers and the OTel wiring from the legacy `Infrastructure/ServiceCollectionExtensions.cs` (both `main` and `rewrite-in-rust-kekw` share this pattern) almost verbatim — same shape, new target (OTLP Collector → Tempo/Prometheus/Loki instead of directly to Jaeger).

3. **`Account` aggregate on Marten — done and runtime-verified** (in `Accounts.Domain` / `Accounts.Infrastructure`)
   - Ported `AccountCreated`, `AccountLocked`, `AccountUnlocked` from legacy `main`'s `Domain/Accounts/*.cs` as Marten event records (`AccountCreated(AccountId Id, GameId BohemiaId, KeycloakUserId KeycloakUserId)`, `AccountLocked`, `AccountUnlocked`) — `KeycloakUserId` is new versus the legacy shape, needed per §1's consequence above.
   - `AccountId`/`GameId`/`KeycloakUserId` as `StronglyTypedId`s; `Account.Create(...)` + `Apply(FooEvent)` shape from `rewrite-in-rust-kekw` kept on the aggregate in `Accounts.Domain` — but the actual Marten-facing `Create`/`Apply` convention methods live on a `partial class AccountProjection : SingleStreamProjection<Account, AccountId>` in `Accounts.Infrastructure`, delegating to the aggregate's own methods. **Do not put convention methods directly on the `Accounts.Domain` type** — Marten's aggregation source generator only runs in a project referencing the `Marten` package, so it silently can't dispatch them there (see `ARCHITECTURE.md §9e`'s verified Marten pattern for the full explanation and three more gotchas hit while building this: `[JsonInclude]` on private setters, unwrapping `StronglyTypedId`s to `.Value` at the Marten API boundary, and the `ELifeRPG.Accounts.*` plural-namespace convention). **Do not re-implement the `DomainEventRegistry`/`DomainEventResolver`/`EventDispatcher` generators either** — that's the specific plumbing Marten replaces.
   - Ported the `Lock()`/`Unlock()` invariant (double-lock/unlock guard from legacy `main`) as the aggregate's decision logic, appending events.
   - End-to-end verified against live Postgres: create → idempotent re-lookup by `BohemiaId` returns the same `AccountId` without duplicating the stream.
   - `Accounts.Infrastructure` gets a `KeycloakUserProvisioner` (or similar): given a `GameId`, creates a Keycloak user (username `bohemia_<uid>`, matching the valid-character constraint verified in §1 — `:` is rejected by Keycloak's username policy) via the Admin REST API, using client-credentials of a realm-admin-scoped service client (separate from `gameserver-dev`, which only needs `manage-users`, not full admin).

4. **Session bootstrap endpoint — done and runtime-verified** (`src/Accounts/Accounts.Api/Sessions/AccountEndpoints.cs`)
   - `POST /api/accounts/session-bootstrap`, **requires** a Bridge-scoped Client Credentials bearer token (`gameserver:session:create`) — a raw `BohemiaId` is never sufficient on its own, closing the gap identified in §1's critical finding. Verified against the real `src/Api` host: no token → `401`; a valid Bridge token → `200` with the account created and a real Keycloak user provisioned; repeating the same call → same `accountId`, no duplicate; a token from a *different* client without the `gameserver:session:create` scope (`account-service`) → `403`, confirming the scope check actually rejects the wrong caller rather than silently passing.
   - Request DTO (in `Accounts.Api`, next to the endpoint): `CreateSessionRequestDto { BohemiaId }` with a `ToCommand()` method mapping to `CreateSessionCommand` — no AutoMapper.
   - Handler (`Accounts.Application`): look up Account by BohemiaId via a Marten projection; if absent, provision a Keycloak user (§3 above) and append `AccountCreated` with the resulting `KeycloakUserId`. If `Locked`, return `403` with an RFC 7807 problem-details body instead of the old `ResultDto.Messages` envelope, per your idiomatic-REST decision.
   - **Correction verified in §4.3:** the Central API does **not** call Keycloak's token-exchange endpoint itself — Keycloak requires the calling client to be the same one the `subject_token` was issued to, so only the Bridge (holding its own client secret) can perform the exchange. On success, the handler just returns the account id/status plus the Keycloak **username** to impersonate; response DTO (in `Accounts.Api`): `SessionDto.Create(account)` — no AutoMapper, no token in this response.
   - Query response shape (e.g. "account found/created vs. locked") is a real native `union` per §9e: `public union CreateSessionResult(CreateSessionResult.Created, CreateSessionResult.Locked) { public record Created(...); public record Locked(...); }`, pattern-matched via `switch` with genuine compiler-checked exhaustiveness. (Took two wrong guesses to find — `union Result { ... }` isn't valid grammar, and `closed record` hierarchies, while real and working, are a different, narrower feature. No `OneOf` dependency either way.)
   - `src/Accounts/Accounts.Api/AccountEndpoints.cs` exposes `AddAccountModule(IServiceCollection)` + `MapAccountModule(WebApplication)`; the `src/Api` host project references only `Accounts.Api` (not `Accounts.Domain`/`Application`/`Infrastructure` directly) and calls both from `Program.cs`.

5. **OpenAPI + Kiota — done and runtime-verified**
   - Central API's OpenAPI document captured to `openapi/eliferpg-api-v1.json` (checked in, per §9c — a build artifact, not just served at runtime, and itself generated deterministically at `dotnet build` time rather than fetched from a running host); `src/Bridge/Bridge.ApiClient` generated from it (`EliferpgApiClient`, `ELifeRPG.Bridge.ApiClient` namespace, matching the `Directory.Build.props` naming convention automatically). `scripts/generate-bridge-client.sh` regenerates both.
   - **Real environment gap hit and fixed:** the Kiota CLI (a dotnet global/local tool) ships targeting a stable .NET runtime (10.0), not the preview one this repo pins in `global.json`. Installing it failed outright with `You must install or update .NET to run this application` until the .NET 10 **runtime** (not SDK — Kiota is a prebuilt tool, not something compiled from source here) was installed side by side. Fixed in `.devcontainer/Dockerfile` so every fresh devcontainer build has it, not just patched into the one running container — verified by building the updated image from scratch and confirming both runtimes coexist and `kiota --version` works.
   - Verified end-to-end (not just that it compiles): a throwaway console app used `EliferpgApiClient` — with a custom `IAccessTokenProvider` fetching a real client-credentials token from Keycloak — to call `POST /api/accounts/session-bootstrap` against the live `src/Api` host, and correctly deserialized the response into the generated `SessionDto` model.
   - CI wiring for automatic regeneration (so client and spec can't silently drift from the live API) is not set up yet — no CI pipeline exists in this repo at all yet, tracked as future work alongside Phase 10.

6. **Bridge Service (minimal slice) — done and runtime-verified**
   - `src/Bridge/Bridge.Host`, a Minimal-API-hosted process (architecturally a Worker Service — a background process on the gameserver host — even though it's built on `WebApplication` rather than the literal Worker Service SDK template, since it needs to expose a local HTTP endpoint) exposing `POST player-connected`, standing in for the mod integration (actual Reforger-side wiring is separate, later work). Later extended with `POST player-disconnected` (ends the Bridge-local session record `player-connected` starts — pure Bridge-side bookkeeping, no Central API involvement) and thin proxy endpoints for the rest of the legacy `/v1` surface (§1.1) — Banking, Characters, and Companies — each translating between a Bridge-local request/response shape and the Kiota-generated `Bridge.ApiClient` models, not exposing those generated types directly (several of them — `BankDto`, `BankAccountDto`, `TransactionResultDto`, `CompanyDto` — hold numeric fields as Kiota's `UntypedNode` wrapper rather than `decimal`/`int`, since Kiota doesn't support OpenAPI's `format: double`/`int32` cleanly; passed through a plain ASP.NET Minimal API response directly, those fields serialize as `{}` instead of a number, confirmed with a throwaway test before writing the real endpoints — `UntypedNode.GetValue()` is the fix).
   - `BridgeTokenProvider` caches the Bridge's own Client Credentials token (refreshed 30s before expiry) and also performs the token exchange directly against Keycloak using that same identity — never through the Central API, per the verified mechanics in §4.3.
   - On a local "player connected" call: invokes the Kiota-generated client (`Bridge.ApiClient`) against the session-bootstrap endpoint to get the account id + Keycloak username; a `403` comes back as Kiota's generated `ProblemDetails` exception (Kiota generates typed exceptions for documented error responses) and is translated to a local `Results.Problem`. If not locked, exchanges for the player-impersonating token directly against Keycloak (`grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `requested_subject=<username>`, its own client credentials) and returns it to the local caller.
   - **Real bug caught and fixed:** `AddHttpClient<BridgeTokenProvider>(...)` followed by a separate `AddSingleton<BridgeTokenProvider>()` is a conflicting double-registration — the second overrides the first, so the actually-resolved instance got an unconfigured `HttpClient` with no `BaseAddress`, failing at runtime (`An invalid request URI was provided`) despite building cleanly. Fixed by registering the named `HttpClient` separately and constructing `BridgeTokenProvider` explicitly as a singleton via `IHttpClientFactory` — necessary anyway since its whole purpose (an in-memory token cache) only works if one instance survives the app's lifetime, which `AddHttpClient<T>()`'s default transient-per-typed-client lifetime doesn't give you.
   - Verified end-to-end for real: `curl` → Bridge's local endpoint → Central API (creates account + provisions Keycloak user) → Bridge exchanges its own token directly against Keycloak → a real, valid player JWT (`preferred_username=bohemia_<uid>`, `azp=gameserver-dev`) comes back to the caller. Repeating the call returns the same `accountId`, confirming idempotency survives the full chain, not just the Central API in isolation.

## 7. Migration Plan: Feature 3 — Banking

**Scope:** the third module, `Banking` — `Bank` (a fee schedule + display name) and `BankAccount` (belongs to exactly one `Character`, holds a cash balance) with deposit/withdraw/transfer. This is the most complex slice so far — the legacy domain (fetched fresh from `github.com/ELifeRPG/Core` for this slice, not just the earlier high-level inventory in §1) has real money-movement logic worth porting faithfully: per-transaction fees (`TransactionFeeBase + Amount * TransactionFeeMultiplier`), ownership checks, insufficient-balance guards, and a transfer that must debit one account and credit another as a single atomic operation.

**Deliberate scope cuts versus the legacy domain (documented, not accidental):**
- **No `Country` entity.** Legacy's `Bank` belongs to a `Country` (used only to generate the bank's national ID number); `Country` was never ported into this codebase at all — even in the legacy app it was "domain-only, unused/future" per §1.2. `Bank` here is just `{ Id, Name, TransactionFeeBase, TransactionFeeMultiplier }`.
- **Personal bank accounts only — no `Company`/Corporate accounts.** Legacy's `BankAccount` can be owned by a `Person` wrapping either a `Character` or a `Company`, with a `BankAccountCapabilities` flags-based permission check against company membership for corporate accounts. The `Companies` module doesn't exist in this codebase yet (§5.1 step 8 deferred it, same as here) and per `ARCHITECTURE.md §9e` a module may not reach into another module's domain directly, so corporate accounts are out of scope until `Companies` exists as a real module with its own `Mediator`-based lookup query. `BankAccount.CharacterId` is the only owner reference.
- **Simplified account number.** Legacy's `BankAccountNumber` is a genuine IBAN-shaped value object with a MOD-97-10 checksum derived from the owning `Bank`'s `Country` code — meaningless without `Country`. Replaced with a short random `EL<11 digits>` string (`OpenBankAccountHandler.GenerateAccountNumber`) — unique and human-typeable, not internationally valid, and not intended to be.
- **Collapsed `BankAccountTransaction` + `BankAccountBooking` into direct domain events.** Legacy models every money movement as a `BankAccountTransaction` (the business event) plus one or two `BankAccountBooking` ledger lines (one per affected account, `Incoming`/`Outgoing`), computed via a `GetType`/`GetAmount` switch keyed on transaction type. This codebase's events *are* the ledger (Marten's event stream for a `BankAccount` already is an append-only record of every balance-affecting thing that happened to it) — `BankAccountDeposited`, `BankAccountWithdrawn`, `BankAccountTransferredOut`, `BankAccountTransferredIn` each carry exactly the fields needed to explain a balance change, no separate booking/transaction split. A transaction-history endpoint (reading the account's own event stream) is not implemented in this slice — deferred, not blocked by anything.
- **New endpoints not in legacy:** `POST /api/banks` (open a bank) and the bank-account-open request taking `characterId` in the body rather than a query parameter. Legacy never exposed bank creation via the API at all — it relied on the `Migrator` console app's seed data, which has no equivalent in this codebase yet. Gated behind a new `gameserver:banking:manage` scope (separate from `gameserver:banking:write`, which covers open-account/deposit/withdraw/transfer) since opening a bank is an operational action, not a player action.

**Cross-module wiring — `CharacterId` promoted to `Shared.Kernel`:** `OpenBankAccountCommand` needs to confirm a `CharacterId` is real before opening an account against it, the same shape of problem `Characters` solved for `Accounts` via `AccountLookupQuery`. Two things had to happen first, both applying the established §9e patterns rather than inventing new ones:
1. `CharacterId` itself moved from `Characters.Domain` to `Shared.Kernel` (mirroring `AccountId`'s earlier move) — any module needing to reference a Character by id, not just `Characters` itself, needs the type without pulling in `Characters.Domain`.
2. A new `CharacterLookupQuery`/`CharacterLookupResult` (`Found(CharacterId, AccountId)` / `NotFound`) added to `Characters.Application`, exactly matching `AccountLookupQuery`'s shape — `Banking.Application` references `Characters.Application` (not `Characters.Domain`/`Infrastructure`) purely to dispatch this query via `IMediator`, same rule as `Characters.Application`'s reference to `Accounts.Application`.

**New pattern established this slice — catching domain guard exceptions in the Application handler, not the endpoint:** `Withdraw`/`TransferOut` throw `BankAccountAuthorizationException`/`InsufficientBalanceException` from the aggregate (same "invariant lives in the domain" convention as `Account.Lock()`'s `AccountStatusException`). Unlike `Accounts`/`Characters` so far, `WithdrawHandler`/`TransferHandler` `catch` these specific exceptions and map them to `WithdrawResult.NotOwner`/`InsufficientBalance` union cases, so the `Api` layer's `switch` stays exhaustive-checked and exception-free — the domain still enforces its own invariants unconditionally (calling `Withdraw` directly, e.g. from a test, still throws), but the Application layer translates that into the same union-result convention used everywhere else. Worth carrying forward: whenever a domain method can throw for a *business* reason (not a programming error), the handler should catch and fold it into the result union rather than letting it become an unhandled 500.

**Verified Marten multi-stream atomic commit (new architectural finding, confirmed against live Postgres):** `TransferHandler` calls `sourceAccount.TransferOut(...)` and `targetAccount.ReceiveTransfer(...)` — two different `BankAccount` aggregates, two different event streams — then appends both events (`IBankAccountRepository.Append<TEvent>`, generic over the event type) to the *same* `IDocumentSession` before a single `SaveChangesAsync()`. Because `MartenBankAccountRepository` owns one session for its whole DI-scoped lifetime (same "repository owns its own session" pattern as `MartenCharacterRepository`), both appends land in one Postgres transaction. Verified two ways: the domain unit test suite doesn't touch Marten at all (so this specifically needed the integration test + manual verification), and the manual end-to-end check confirmed real numbers — source account debited `Amount + Fee`, target credited exactly `Amount`, both changes visible via `GET /api/bank-accounts/{id}` immediately after the transfer call returned, no partial-update window observed.

**Done and runtime-verified (2026-08-14):**
- `src/Banking/{Banking.Domain, Banking.Application, Banking.Infrastructure, Banking.Api}` — `Bank`/`BankAccount` aggregates, both hosted in one secondary Marten store (`IBankingStore`, schema `banking`) — the first module to put two different aggregate types in the same store, confirmed to work without cross-registration issues.
- `Banking.Application.csproj` referenced only `Mediator.Abstractions` from the start this time (the `CS0121` ambiguous-dispatcher bug from `MIGRATION.md §6` was caught and turned into an explicit rule in `ARCHITECTURE.md §9e`, so it didn't recur here) — full-solution build succeeded on the first attempt after wiring the host.
- `tests/Banking.Domain.UnitTests` (11 tests: fee calculation, deposit/withdraw/transfer balance math, ownership guard, insufficient-balance guard, same-account-transfer guard) and `tests/Banking.IntegrationTests` (8 tests against live Postgres/Keycloak: open bank account for a known/unknown character, deposit, withdraw by owner/non-owner/with insufficient balance, and the atomic two-account transfer verified via a follow-up `BankAccountDetailsQuery` on both accounts) — all passed on the first run, no bugs found this slice (unlike `Accounts`/`Characters`, where runtime verification caught real defects — attributed to proactively applying every previously-documented `ARCHITECTURE.md §9e` gotcha up front rather than discovering them fresh).
- End-to-end verified through the real running `src/Api` host: minted a token (confirmed `gameserver:banking:manage`/`gameserver:banking:write` scopes present), bootstrapped an account, created a character, opened a bank (`POST /api/banks`), listed banks, opened two bank accounts for the same character, deposited 100 (fee `2.20`, balance `97.80`), withdrew 20 (fee `0.60`, balance `77.20`), transferred 30 to the second account (fee `0.80`; source → `46.40`, target → exactly `30`, confirmed via `GET` on both), and verified all four error paths for real: non-owner withdraw → `403`, over-balance withdraw → `409`, transfer to an unknown target → `404`, no bearer token → `401`. Test Keycloak user cleaned up afterward; Marten rows (including ~25 `"Test Bank"` rows left behind by repeated integration test runs) left in place — dev-only data, same cleanup policy as `Accounts`/`Characters`.
- `gameserver:banking:manage` and `gameserver:banking:write` client scopes added to both the running dev Keycloak instance and the version-controlled `infra/keycloak/eliferpg-realm.json` export.

**Not done in this slice (deferred):** transaction-history endpoint (reading an account's own event stream — see the scope-cuts note above; built later, see §10), any endpoint requiring `Companies` (corporate bank accounts), OpenAPI/Kiota regeneration for the new endpoints (same "no CI yet" gap as previous slices), input validation for non-positive deposit/withdraw/transfer amounts (the domain throws a plain `ArgumentOutOfRangeException` for this, which surfaces as an unhandled `500` rather than a clean `400` — legacy had no such validation either, but this codebase's own "closing gaps" premise means it's worth fixing before this module is considered done, not just migrated).

The Banking module is now the reference example for a module that needs a *second* cross-module lookup query and a multi-aggregate atomic operation, the same way `Accounts` was the reference for the base pattern and `Characters` was the reference for a single cross-module reference.

## 9. Corporate Bank Accounts (Banking ↔ Companies)

**Scope:** the piece `Banking §7` explicitly deferred pending a real `Companies` module — `BankAccount` now supports two owner kinds (`BankAccountType.Personal`/`Corporate`, matching legacy's own enum), with a `Corporate` account's withdraw/transfer authorization resolved by asking `Companies` whether the acting character has `CompanyPermissions.ManageFinances` in that company. Not a new module — a real cross-module capability added to `Banking`, requiring one additive change to `Companies` first.

**Prerequisite change to `Companies` — seeding an "Owner" position:** `CompanyCreated` previously seeded only the single "Rookie" position (`§8`); every member, including a freshly-created company's founder, ended up with `CompanyPermissions.None`. That made corporate authorization untestable in practice — there would have been no way for *any* character to ever pass the `ManageFinances` check, since no position with that permission could ever exist (legacy never implemented position management either, so this dead end existed in legacy too, just never noticed because legacy had no corporate-account authorization path exercising it). Fixed by seeding a second position, "Owner" (`Ordering` 1, every `CompanyPermissions` flag set), and having `CreateCompanyHandler` add the founder to it explicitly (`company.AddMember(founderCharacterId, ownerPositionId)`) instead of relying on the default-position resolution (which still correctly falls through to "Rookie", `Ordering` 10, for everyone added afterward via `AddMemberCommand`). Position *management* (adding further custom positions beyond these two seeded ones) is still not implemented — this only adds the one extra position needed to make ownership and corporate authorization meaningful, not general position CRUD.

**Domain change — authorization moved out of the aggregate, since Domain can't cross-module-query:** `BankAccount.Withdraw`/`TransferOut` previously compared the acting `CharacterId` against a single stored owner field internally (`EnsureOwner`). That doesn't generalize to Corporate accounts, whose authorization depends on a company membership + position lookup — a cross-module `Mediator` query, which `*.Domain` projects are never allowed to make (see `ARCHITECTURE.md §9e`'s dependency rules). Both methods now take an `isAuthorized: bool` computed by the caller instead of doing the check themselves: `Withdraw(CharacterId actingCharacterId, bool isAuthorized, decimal amount)`. `actingCharacterId` is still always recorded on the resulting event regardless of ownership type, for audit purposes — only *how authorization is decided* moved, not *who gets remembered as having done it*. A new `Banking.Application.Common.BankAccountAuthorization.IsAuthorizedAsync` helper (shared by `WithdrawHandler` and `TransferHandler`) does the actual resolution: `Personal` compares `OwnerCharacterId`; `Corporate` dispatches a new `CompanyMemberPermissionsQuery` into `Companies.Application` and checks the returned `CompanyPermissions` for `ManageFinances`.

**Two new cross-module queries added to `Companies.Application`,** both deliberately narrower than the module's own `CompanyDetailsQuery` (which returns the full `Company` aggregate — fine for `Companies.Api`'s own use, but exposing positions/memberships to *another* module would violate the "expose minimal fields" convention `AccountLookupQuery`/`CharacterLookupQuery` established):
- `CompanyLookupQuery(CompanyId) → Found(CompanyId, Name) | NotFound` — company existence check for `OpenCorporateBankAccountCommand`.
- `CompanyMemberPermissionsQuery(CompanyId, CharacterId) → Found(CompanyPermissions) | NotMember` — the authorization check itself.

**`BankAccountOpened` event reshaped:** `CharacterId CharacterId` replaced with `BankAccountType Type, CharacterId? OwnerCharacterId, CompanyId? OwnerCompanyId` (exactly one owner field set, enforced by construction — `OpenBankAccountCommand` only ever sets the Character one, the new `OpenCorporateBankAccountCommand` only ever sets the Company one — not by the record itself). Since this is all still pre-release dev data, the event schema was freely changed rather than versioned/migrated.

**New `OpenCorporateBankAccountCommand`,** a separate command from `OpenBankAccountCommand` rather than one command with two nullable owner fields — keeps each command's invariants unambiguous (no "both set"/"neither set" state to guard against inside the handler). The wire-level API stays unified though: `POST /api/banks/{bankId}/accounts` accepts a request body with `characterId`/`companyId`, exactly one of which must be set (`400` otherwise), and the endpoint dispatches to whichever command applies — this mirrors the legacy endpoint's own shape (one route, either a `characterId` or `companyId` query parameter).

**Verified Marten gotcha — nullable `StronglyTypedId` LINQ filters, previously untested:** `MartenBankAccountRepository.FindByCharacterIdAsync`/`FindByCompanyIdAsync` needed to filter on `CharacterId?`/`CompanyId?` properties (`x.OwnerCharacterId != null && x.OwnerCharacterId!.Value.Value == characterId.Value`) — a shape no earlier module's queries needed, since every prior strongly-typed-id LINQ filter (`AccountId`, `CharacterId` alone) was non-nullable. This worked correctly against live Postgres on the first attempt, confirmed by a new integration test (`BankAccountsByCharacterQuery_DoesNotIncludeCorporateAccounts`) that only passes if the nullable-field filter actually excludes accounts with a null `OwnerCharacterId`, not just accidentally matches everything.

**Real discovery — `Mediator.SourceGenerator` allows only one `AddMediator(...)` call site per compiled assembly:** adding a second integration test class (`CorporateBankAccountTests`) to `Banking.IntegrationTests`, each with its own `InitializeAsync` calling `services.AddMediator(options => options.Assemblies = [...])` with an *identical* assembly list to the existing `BankingCommandTests`, failed to build with `MSG0007: Assemblies can only be configured once` — the generator scans the whole compilation for `AddMediator` call sites and only supports exactly one, regardless of whether multiple call sites agree on the configuration. Not something any earlier module's test project hit, since none of them had more than one integration test *class* in the same project before. Fixed by extracting a shared `TestServices.BuildProvider()` static factory containing the single `AddMediator` call, used by every test class in the project — a pattern worth reusing for any future test project that grows a second test class.

## 10. Bank Account Transaction History

**Scope:** the transaction-history endpoint deferred back in `§7` — `GET /api/bank-accounts/{id}/transactions`, returning an account's most recent money-movement events, newest first, capped at 30 (matching legacy's own hardcoded `Take(30)` on `BankAccountBooking`s). No new write-side work: the account's own Marten event stream already *is* the ledger (per `§7`'s "collapsed `BankAccountTransaction`/`BankAccountBooking`" note) — this just reads it back out in a display-friendly shape.

**New domain read-model, not a new event:** `BankAccountTransactionRecord(OccurredAt, Kind, Amount, Fee, CounterpartyBankAccountId?, ActingCharacterId?)` and a `BankAccountTransactionKind` enum (`Deposited`/`Withdrawn`/`TransferredOut`/`TransferredIn`) unify the four existing event shapes for display — it's a projection built at query time from `BankAccountDeposited`/`Withdrawn`/`TransferredOut`/`TransferredIn`, never itself appended as an event. `IBankAccountRepository.GetHistoryAsync` reads the raw stream via `session.Events.FetchStreamAsync(id)` and maps each event's `.Data` to the matching `BankAccountTransactionRecord` shape (a `switch` on runtime type); `BankAccountOpened` is filtered out (legacy's bookings never included account-opening either — only deposit/withdrawal/transfer are "transactions"). The query handler checks the account exists first (`FindByIdAsync`) before reading history, since a nonexistent stream and an empty-but-real one both read back as an empty list from Marten — `GetHistoryAsync` alone can't distinguish "no such account" from "no transactions yet."

**Verified Marten gotcha — `IEvent` lives in `JasperFx.Events`, not `Marten.Events`:** the same package relocation hit earlier for `ProjectionLifecycle` (Marten 9.x moved core event-sourcing types into the separate `JasperFx.Events` package) — mentioned in passing during the `Accounts` slice but never actually written down as its own `ARCHITECTURE.md §9e` gotcha until now (see gotcha 8 there, added alongside this feature). `using Marten.Events;` compiles (the namespace exists) but doesn't contain `IEvent`, producing `CS0246`; the fix is `using JasperFx.Events;`. Hit again here because `session.Events.FetchStreamAsync` returns `IReadOnlyList<IEvent>` — a different corner of the Marten API than the projection-lifecycle enum that first surfaced this relocation.

**Done and runtime-verified (2026-08-14):**
- `Banking.Domain`: `BankAccountTransactionRecord`, `BankAccountTransactionKind`. `Banking.Application`: `BankAccountTransactionHistoryQuery` (`Found(IReadOnlyList<BankAccountTransactionRecord>)`/`BankAccountNotFound`), `IBankAccountRepository.GetHistoryAsync`. `Banking.Infrastructure`: `MartenBankAccountRepository.GetHistoryAsync` + the event-to-record mapping. `Banking.Api`: `BankAccountTransactionDto`, `GET /api/bank-accounts/{bankAccountId}/transactions` (same auth as the existing details endpoint — any authenticated caller, no specific scope; only *mutating* an account is scope-gated).

## 12. Shops

**Scope:** a new module, `Shops` — a `Character`- or `Company`-owned shop lists `Items` catalog entries for sale at a price with finite stock; another character can purchase a listing, settled by moving money from their own bank account to the shop's payout account via `Banking`'s existing `TransferCommand`. Revives the intent of the old `ELifeRPG/Core` `89-shops` branch (`Shop`/`ShopListing`/`Item`/`Prefab`, owned by a `Character` or `Company`) — that branch was a single-commit domain skeleton with no pricing, no purchase flow, and no Application/Api layer (confirmed by inspecting it directly), so nothing was ported beyond the ownership shape and vocabulary.

**Two aggregates on separate Marten streams (`Shop`, `ShopListing`), not one with an embedded collection** — mirrors the existing `Bank`/`BankAccount` split rather than the legacy branch's single `Shop.Listings`, so concurrent purchases against *different* listings in the same shop never serialize against each other.

**`BankAccountId` promoted to `Shared.Kernel`:** `Shop.PayoutBankAccountId` is the first cross-module reference to it (previously `Banking`-internal only) — moved the same way `CharacterId`/`CompanyId` were for their own first cross-module consumer.

**New `CompanyPermissions.ManageShops` flag**, checked cross-module by `Shops.Application`'s `ShopAuthorization` exactly the way `ManageFinances` already gates a Corporate `BankAccount` — the second real enforcement of a `CompanyPermissions` flag in this codebase (after `ManageFinances`, and `ManageMembers` for company applications).

**Purchase saga corrected during planning, not just implementation:** the initial design had payment happen before the stock decrement, with a compensating reverse transfer refunding the buyer if the decrement then failed — that reverse transfer turns out to be unauthorizable, since `Banking`'s `TransferCommand` requires the acting character to own (or hold a permission on) the *source* account, and the buyer is never authorized on the *shop's* payout account. Reordering to reserve stock first and charge second avoids the problem entirely: a failed payment after a successful stock reservation is restored via `ShopListing.RestoreStock`, an in-module operation needing no cross-module authorization at all.

**First real use of Marten's `FetchForWriting` optimistic-concurrency API in this codebase:** every prior repository just calls `Append` without expected-version tracking; `IShopListingRepository.PurchaseAsync` needed genuine "two writers, one stream, only one may win" protection, since two concurrent purchases against the same listing must never both succeed. The concurrency-conflict exception turned out not to be `Marten.Exceptions.ConcurrencyException` as first guessed — Marten 9's event-store concurrency exception is `JasperFx.ConcurrencyException`, the same package-relocation pattern `ARCHITECTURE.md` §9e gotcha 8 already documents for `IEvent`/`ProjectionLifecycle` — confirmed the hard way, since the guessed type name didn't even compile. Verified under a real concurrent-request race (`Purchase_TwoConcurrentBuyersForLastUnit_ExactlyOneSucceeds`), not just asserted from documentation.

**Built with gameserver tenancy from day one, not retrofitted:** `main`'s multi-gameserver tenancy work landed on `main` after this plan was originally written, mid-execution — merged into this branch and incorporated into `Items`/`Shops` rather than shipped as a fresh gap. Both modules follow the exact `Banking`/`Characters`/`Companies` pattern: `ICurrentGameServer`/`HttpContextCurrentGameServer` per module, `TenancyStyle.Conjoined` + `AllDocumentsAreMultiTenanted()` on both Marten stores, every repository session opened via `LightweightSession(currentGameServer.ClientId)`, and every read endpoint gated behind the module's scope policy rather than left as plain `.RequireAuthorization()`. `ShopsHub.SubscribeToShop` additionally closes a side channel the REST-only pattern didn't need to consider: it validates the target shop belongs to the caller's own tenant (via `Context.User`'s `client_id` claim and a direct tenant-scoped `IShopsStore` query) before joining the caller's connection to that shop's update group — otherwise a caller holding another tenant's `shopId` could still receive its live listing pushes even though `GET /api/shops/{shopId}` would 404 for them.

> **Historical note (2026-08-22):** the gameserver-tenancy model described in this paragraph — conjoined multi-tenancy per gameserver instance, spanning all five modules including `Items` and `Shops` — was later removed entirely. One deployment is now a single hive of servers sharing one world; `Items` and `Shops` lost their tenancy wiring the same as `Characters`/`Banking`/`Companies` did. See `ARCHITECTURE.md` §4.1. This paragraph is kept as-written for history, not as current behavior.

**First SignalR hub in the codebase:** `ShopsHub` pushes `ListingChanged`/`ListingRemoved` to per-shop subscriber groups after a mutating REST endpoint's `Mediator` call succeeds — a simpler, purpose-built mechanism than the "Marten subscription feeds a hub" pipeline `ARCHITECTURE.md §5.3` sketches for the Bridge/NPC raw event-batch case, which nothing has needed yet. Required one host-level change: `Program.cs`'s shared `JwtBearerEvents` now also reads a bearer token from the `access_token` query string on `/hubs` paths, since a browser can't set a custom header on a WebSocket upgrade — this is authentication plumbing usable by any future hub, not `Shops`-specific logic, so it lives in the host's existing central config next to the token-revocation check already there.
